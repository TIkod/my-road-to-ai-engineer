## 1. Что такое LLM API

Модель работает на серверах провайдера. Чтобы ей воспользоваться, твой код отправляет **HTTP-запрос** (POST с JSON) и получает ответ. Это обычный REST API, как любой другой внешний сервис в твоём backend.

```
 Твой код (Python)                                Провайдер (Groq, OpenAI, Anthropic...)
 ─────────────────                                ──────────────────────────────────────
 client.chat.completions.create(...)
        │
        │  POST https://api.groq.com/openai/v1/chat/completions
        │  Authorization: Bearer <API-ключ>
        │  {"model": "...", "messages": [...], "max_tokens": 300}
        └──────────────────────────────────────────►  токенизация → модель → генерация
                                                                │
        ┌───────────────────────────────────────────────────────┘
        │  {"choices": [{"message": {"content": "..."}}], "usage": {...}}
        ▼
 response.choices[0].message.content
```

Три вещи, которые нужны для запроса:

| Что | Зачем | Где взять |
|---|---|---|
| **API-ключ** | Провайдер понимает, кто ты, и считает твои лимиты и расходы | Консоль провайдера (`console.groq.com/keys`) |
| **Адрес API (`base_url`)** | Куда отправлять запрос | Документация провайдера |
| **Название модели** | Какую из моделей провайдера использовать | Список моделей в консоли или через API |

**SDK** (библиотека `openai`) — это обёртка над HTTP. Она сама собирает запрос, подставляет ключ, разбирает JSON в объекты, повторяет запрос при временных сбоях. Писать HTTP руками не нужно.

**Формат OpenAI — фактический стандарт.** Его эндпоинт `/chat/completions` поддерживают Groq, Ollama, OpenRouter, Together, vLLM и многие другие. Поэтому один и тот же код работает с разными провайдерами: меняются только `base_url`, ключ и модель.

## 2. Подготовка окружения

Один раз, из корня репозитория:

```bash
python3 -m venv .venv                  # виртуальное окружение
source .venv/bin/activate              # активировать (в каждом новом терминале)
pip install -r requirements.txt        # поставить зависимости
cp .env.example .env                   # создать файл с ключами и вписать туда свой ключ
```

Запуск любого примера:

```bash
python part2/code/01_first_request.py
```

### Правила работы с ключами

- **Ключ хранится только в `.env`**, а `.env` добавлен в `.gitignore`. В git попадает только `.env.example` с заглушкой: по нему видно, какие переменные нужны.
- **Никогда не пиши ключ прямо в коде** и не присылай его в чаты. Если ключ утёк (например, попал в публичный репозиторий), сразу удали его в консоли и создай новый.
- В коде ключ читается из переменных окружения. Библиотека `python-dotenv` загружает их из `.env`.

### Общий модуль подключения

Все примеры подключаются через [`code/llm_client.py`](code/llm_client.py). Настройки провайдеров собраны в одном месте:

Это первый шаг к требованию этапа 1 роадмапа: «сервис переключается между двумя провайдерами». Чтобы сменить провайдера, достаточно поменять одно слово.

### Модели Groq на момент написания

| Модель | Особенность |
|---|---|
| `qwen/qwen3.8-27b` | Самая быстрая, без скрытых «размышлений». **Используем по умолчанию** |
| `openai/gpt-oss-20b` | Сначала «думает», потом отвечает |
| `openai/gpt-oss-120b` | Крупнее и умнее, тоже «думает» |

Список моделей у Groq меняется. Актуальный можно получить кодом: `client.models.list()`. У новых аккаунтов модели бывают выключены, и API отвечает `403 ... blocked at the organization level`. Тогда их нужно разрешить в консоли: `console.groq.com/settings/limits`.

## 3. Первый запрос: из чего он состоит

Скрипт [`code/01_first_request.py`](code/01_first_request.py):

```python
from llm_client import get_client

client, model = get_client("groq")

response = client.chat.completions.create(
    model=model,
    messages=[
        # system — правила поведения на весь диалог
        {"role": "system", "content": "Ты ассистент интернет-магазина электроники. Отвечай кратко, на русском."},
        # user — сообщение пользователя
        {"role": "user", "content": "Какие наушники лучше для спорта: накладные или вкладыши?"},
    ],
    max_tokens=300,  # максимум токенов в ответе
)

choice = response.choices[0]
print("Ответ модели:\n", choice.message.content)
print("\nПочему остановилась (finish_reason):", choice.finish_reason)
print("Модель:", response.model)
print("Токены: вход =", response.usage.prompt_tokens,
      "| выход =", response.usage.completion_tokens,
      "| всего =", response.usage.total_tokens)
```

Вывод (ответ сокращён):

```
Ответ модели:
 Для спорта выбор зависит от типа нагрузки:

1.  **Вкладыши (включая TWS):**
    *   **Плюсы:** Компактность, эргономика, современные модели влагозащищены (IPX4/IPX7)...
...
Но для большинства спортсменов **вкладыши с хорошими амбушюрами** — оптимальный вариант.

Почему остановилась (finish_reason): stop
Модель: qwen/qwen3.8-27b
Токены: вход = 53 | выход = 280 | всего = 333
```

### Параметры запроса

| Параметр | Что это |
|---|---|
| `model` | Какую модель вызвать |
| `messages` | Список сообщений: весь контекст, который увидит модель |
| `max_tokens` | Потолок длины ответа в токенах |
| `stream` | Отдавать ответ по кусочкам (раздел 6) |
| `temperature` | Случайность выбора токена (part 1, шаг 6). У Groq и OpenAI есть, у текущих моделей Claude убран |

### Роли сообщений

| Роль | Кто пишет | Зачем |
|---|---|---|
| `system` | Ты, разработчик | Правила на весь диалог: кто модель, как отвечать, чего не делать. Пользователь его не видит |
| `user` | Пользователь | Вопросы и сообщения |
| `assistant` | Модель | Её прошлые ответы. Ты кладёшь их в историю сам (раздел 5) |

Позже появится ещё роль `tool` — результаты вызова инструментов (part 3).

### Важное наблюдение: `max_tokens` не делает ответ короче

В system prompt написано «Отвечай кратко», а модель выдала 280 токенов со списками и заголовками. `max_tokens=300` её не сократил: он только **обрезает** ответ, если тот не влез. Модель о лимите не знает и не подстраивается под него.

- **Длину и формат ответа задают в промпте:** «1–2 предложения», «без списков», «не больше 50 слов».
- `max_tokens` — это **защита от слишком длинного и дорогого ответа**, а не способ управлять длиной.

## 4. Из чего состоит ответ

```
response
├── model             — какая модель ответила
├── choices[0]
│   ├── message
│   │   ├── role      — "assistant"
│   │   └── content   — текст ответа
│   └── finish_reason — почему модель остановилась
└── usage
    ├── prompt_tokens      — входные токены
    ├── completion_tokens  — выходные токены (включая скрытые «размышления»)
    └── total_tokens
```

`choices` — список, потому что можно попросить несколько вариантов ответа сразу. Почти всегда используется один: `choices[0]`.

### `finish_reason`: почему модель остановилась

| Значение | Что значит | Что делать |
|---|---|---|
| `stop` | Модель закончила ответ сама | Всё нормально |
| `length` | Упёрлась в `max_tokens`, ответ **обрезан** | Увеличить `max_tokens` или попросить отвечать короче. Обрезанный ответ нельзя показывать как полный, а обрезанный JSON не распарсится |
| `tool_calls` | Модель хочет вызвать инструмент | Part 3 |

**Всегда проверяй `finish_reason`.** Ответ с `length` приходит как успешный (HTTP 200), без исключения. Если не проверять, обрезанный текст молча уйдёт пользователю.

### `usage`: что показали живые замеры

Один и тот же вопрос («Что такое токен в LLM? Одним предложением.» с одинаковым system prompt) на трёх моделях Groq:

| Модель | Время | Вход | Выход | Из них «размышления» |
|---|---|---|---|---|
| `qwen/qwen3.8-27b` | 0.24 с | 48 | 37 | — |
| `openai/gpt-oss-20b` | 0.62 с | 104 | 192 | **147** |
| `openai/gpt-oss-120b` | 0.88 с | 104 | 95 | 47 |

Что отсюда следует:

1. **Одинаковый текст — разное число входных токенов** (48 против 104). У моделей разные токенизаторы и разная служебная разметка ролей (part 1, шаг 2). Считать токены нужно для конкретной модели, а точнее всего брать их из `usage`.
2. **«Думающие» модели тратят выходные токены на рассуждения.** У `gpt-oss-20b` 147 из 192 выходных токенов ушли на скрытые размышления, а сам ответ — одно предложение. Эти токены **оплачиваются и съедают лимиты** как обычный выход. Для простых задач «думающая» модель может быть в разы дороже и медленнее при том же результате.
3. **Модель крупнее не всегда медленнее и дороже.** `gpt-oss-120b` здесь подумала меньше, чем 20b. Сравнивать модели нужно замерами на своих задачах, а не по названию.

## 5. Диалог: как бот «помнит» историю

Из part 1 (шаг 9): у модели нет памяти между запросами. «Память» — это список `messages`, который ты хранишь сам и отправляешь целиком в каждом запросе.

Ключевая часть [`code/02_chat_history.py`](code/02_chat_history.py):

```python
messages = [
    {"role": "system", "content": "Ты дружелюбный ассистент. Отвечай кратко, 1-2 предложения, на русском."},
]

while True:
    user_text = input("\nТы: ").strip()
    ...
    messages.append({"role": "user", "content": user_text})

    response = client.chat.completions.create(model=model, messages=messages, max_tokens=300)
    answer = response.choices[0].message.content

    # Ответ модели тоже кладём в историю — иначе в следующем запросе она его «не вспомнит»
    messages.append({"role": "assistant", "content": answer})
```

Вывод:

```
Ты: Привет! Меня зовут Олег.
Бот: Привет, Олег! Рада познакомить с тобой. Чем могу помочь?
   [сообщений в истории: 3, входных токенов в этом запросе: 53]

Ты: Посоветуй, чем заняться вечером в пятницу.
Бот: Можно устроить уютный вечер с фильмом, настолками или посидеть с друзьями. ...
   [сообщений в истории: 5, входных токенов в этом запросе: 96]

Ты: А как меня зовут?
Бот: Тебя зовут Олег.
   [сообщений в истории: 7, входных токенов в этом запросе: 153]
```

Видно сразу две вещи:
- Бот «помнит» имя только потому, что первое сообщение лежит в `messages` и уходит в каждом запросе.
- **Входные токены растут с каждым сообщением: 53 → 96 → 153.** Ты платишь за всю историю на каждом запросе. В реальном боте историю хранят в Redis или PostgreSQL, а длинную обрезают или сжимают (part 1, шаг 9.4).

## 6. Стриминг

Без стриминга пользователь ждёт, пока модель сгенерирует весь ответ. Со стримингом текст появляется сразу, по кусочкам (part 1, шаг 7).

Ключевая часть [`code/03_streaming.py`](code/03_streaming.py):

```python
stream = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "Напиши короткое стихотворение (4 строки) про программиста и кофе."}],
    max_tokens=300,
    stream=True,                              # включаем стриминг
    stream_options={"include_usage": True},   # попросить токены в последнем кусочке
)

for chunk in stream:
    if chunk.usage:            # в последнем кусочке приходит usage и нет текста
        usage = chunk.usage
    if not chunk.choices:
        continue
    piece = chunk.choices[0].delta.content
    if piece:
        print(piece, end="", flush=True)  # печатаем сразу, не дожидаясь конца
```

Вывод:

```
Пустая чашка — верный знак,
Что код не сходит с первого дна.
А кофе — лучший идеал,
Чтоб дедлайн не сливал себя в пустоту.

TTFT (время до первого токена): 0.69 с
Время всего ответа:             0.83 с
Токены: вход = 33, выход = 46
Скорость генерации: ~334 токенов/с
```

(Стихи у маленькой быстрой модели так себе, но механика видна.)

### Чем стриминг отличается в коде

| | Без стриминга | Со стримингом |
|---|---|---|
| Что возвращает `create()` | Готовый объект ответа | Итератор кусочков (chunks) |
| Где текст | `response.choices[0].message.content` | `chunk.choices[0].delta.content` в каждом кусочке. Склеивать самому |
| Где токены | `response.usage` | В последнем кусочке, если передать `stream_options={"include_usage": True}` |

### Метрики

- **TTFT** (time to first token) — сколько пользователь смотрит на пустой экран. Именно её стриминг улучшает.
- **Скорость генерации** (токенов в секунду) — как быстро «печатается» ответ. У Groq она очень высокая (~330 токенов/с здесь), у других провайдеров обычно ниже.

### Как это будет в backend

В FastAPI стрим от провайдера пробрасывают клиенту через **SSE** (Server-Sent Events) с помощью `StreamingResponse`: каждый кусочек сразу отправляется в браузер или Telegram-боту. Это одна из задач итогового проекта этапа 1.

## 7. Ошибки и надёжность

LLM API — это внешний сервис по сети. Он может не ответить, упереться в лимит, отказать в доступе. Скрипт [`code/04_errors.py`](code/04_errors.py) специально вызывает пять типичных проблем:

```
=== Ответ не влез в max_tokens ===
Успех. finish_reason = length
Текст: 'История интернета — это увлекательное путешествие от военных проектов в'

=== Несуществующая модель ===
404 NotFoundError: Error code: 404 - The model `qwen/no-such-model` does not exist or you do not ha

=== Неверный API-ключ ===
401 AuthenticationError: Error code: 401 - Invalid API Key

=== Сервер недоступен ===
APIConnectionError: не удалось подключиться

=== Таймаут ===
APITimeoutError: истёк таймаут
```

Обработка — цепочка `except` **от частного к общему**:

```python
try:
    response = client.chat.completions.create(...)
except openai.AuthenticationError:   # 401: неверный ключ
    ...
except openai.NotFoundError:         # 404: нет такой модели
    ...
except openai.RateLimitError:        # 429: превышен лимит
    ...
except openai.APIStatusError as e:   # любой другой HTTP-ответ с ошибкой
    ...
except openai.APITimeoutError:       # истёк таймаут (подкласс APIConnectionError — ловить раньше)
    ...
except openai.APIConnectionError:    # не удалось соединиться
    ...
```

### Какие ошибки повторять, а какие нет

| Ошибка | Код | Повторять? | Почему |
|---|---|---|---|
| `BadRequestError` | 400 | Нет | Ошибка в запросе. Повтор вернёт то же самое |
| `AuthenticationError` | 401 | Нет | Неверный ключ |
| `PermissionDeniedError` | 403 | Нет | Нет доступа (как с выключенными моделями Groq) |
| `NotFoundError` | 404 | Нет | Нет модели или адреса |
| `RateLimitError` | 429 | **Да**, с паузой | Превышен лимит запросов. Подождать и повторить |
| `InternalServerError` | 5xx | **Да** | Сбой на стороне провайдера |
| `APIConnectionError` / `APITimeoutError` | — | **Да** | Проблемы сети или перегрузка |
| `finish_reason == "length"` | 200 | Не исключение | Ответ обрезан. Это нужно проверять отдельно |

**Нельзя ловить всё одним `except Exception`.** Тогда неверный ключ и временный сбой сети обрабатываются одинаково: либо ты бесконечно повторяешь запрос с плохим ключом, либо сдаёшься при первой сетевой ошибке.

### Что SDK делает за тебя

- **Автоповторы.** SDK `openai` сам повторяет запрос при ошибках соединения, 408, 409, 429 и 5xx: по умолчанию **2 раза** с нарастающей паузой. Настраивается через `max_retries` при создании клиента. В логе скрипта 05 это видно: `Retrying request in 0.39 seconds (retry 1 of 1)`.
- **Таймаут.** По умолчанию 10 минут. Для чат-бота это слишком долго: пользователь не будет ждать. Ставь свой: `OpenAI(..., timeout=30)`.
- Учти, что таймаут срабатывает **на каждую попытку**. С `timeout=30` и `max_retries=2` запрос может длиться до 90 секунд.

## 8. Несколько провайдеров, fallback и логирование

### Fallback

Если основной провайдер недоступен, запрос уходит к запасному. Ключевая часть [`code/05_fallback_and_logging.py`](code/05_fallback_and_logging.py):

```python
def ask(messages: list[dict], providers: list[str], max_tokens: int = 300) -> str:
    """Пробует провайдеров по порядку. Возвращает текст первого успешного ответа."""
    for provider in providers:
        client, model = get_client(provider, max_retries=1, timeout=30)
        start = time.perf_counter()
        try:
            response = client.chat.completions.create(model=model, messages=messages, max_tokens=max_tokens)
        except (openai.APIConnectionError, openai.RateLimitError, openai.InternalServerError) as e:
            # Временные проблемы: имеет смысл попробовать следующего провайдера
            log.warning("provider=%s недоступен (%s), пробуем следующего", provider, type(e).__name__)
            continue

        usage = response.usage
        log.info("provider=%s model=%s in=%d out=%d time=%.2fs cost≈$%.6f finish=%s", ...)
        return response.choices[0].message.content

    raise RuntimeError("Все провайдеры недоступны")


answer = ask(messages=[...], providers=["ollama", "groq"])  # сначала локальный, при сбое — облачный
```

Вывод (Ollama не установлен, поэтому срабатывает fallback):

```
22:38:42 INFO Retrying request in 0.393717 seconds (retry 1 of 1)
22:38:42 WARNING provider=ollama недоступен (APIConnectionError), пробуем следующего
22:38:43 INFO HTTP Request: POST https://api.groq.com/openai/v1/chat/completions "HTTP/1.1 200 OK"
22:38:43 INFO provider=groq model=qwen/qwen3.8-27b in=44 out=109 time=0.64s cost≈$0.000059 finish=stop
```

**На какие ошибки переключаться:** только на временные (сеть, 429, 5xx). На 400, 401, 404 переключаться бессмысленно или опасно: ошибка в твоём запросе или настройках, и у запасного провайдера она, скорее всего, повторится или замаскирует проблему.

**Подвох fallback:** у разных провайдеров разные модели, а значит, разное качество, формат и цена ответов. Если основная модель упала, пользователь получит ответ от другой модели. Это нужно учитывать в промптах и проверять evals.

### Логирование

Для каждого запроса в лог пишется: провайдер, модель, входные и выходные токены, время, примерная цена, `finish_reason`. Это прямо критерий этапа 1 роадмапа: «пишет в лог токены и цену каждого запроса».

Зачем это нужно:
- видно, **где уходят деньги**: какие запросы самые дорогие, растёт ли история;
- видно, **где теряется время**;
- `finish_reason=length` в логах сразу показывает обрезанные ответы.

**Цена.** Groq на бесплатном тарифе ничего не стоит, поэтому в примере цена считается по тарифу платной модели (Claude Haiku 5.5: $0.10 вход / $0.50 выход за 1M токенов). Формула та же, что в part 1, шаг 11. В продакшене цены выносят в конфиг: они меняются.

## 9. Чем отличается API Claude

У Anthropic свой формат (Messages API) и свой SDK `anthropic`. Идеи те же, отличаются детали. Пример из раздела 3 на Claude:

> Не запускался: нужен платный ключ Anthropic.

```python
import anthropic

client = anthropic.Anthropic()  # ключ из переменной окружения ANTHROPIC_API_KEY

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    system="Ты ассистент интернет-магазина электроники. Отвечай кратко, на русском.",  # отдельный параметр
    messages=[
        {"role": "user", "content": "Какие наушники лучше для спорта: накладные или вкладыши?"},
    ],
)

# content — список блоков (текст, размышления, вызовы инструментов); берём текстовые
text = "".join(block.text for block in response.content if block.type == "text")
print(text)
print("stop_reason:", response.stop_reason)
print("Токены: вход =", response.usage.input_tokens, "| выход =", response.usage.output_tokens)
```

| | Формат OpenAI (Groq, Ollama...) | Claude (Anthropic) |
|---|---|---|
| Метод | `client.chat.completions.create` | `client.messages.create` |
| System prompt | Сообщение с `role: "system"` в `messages` | Отдельный параметр `system=...` |
| `max_tokens` | Необязательный | **Обязательный** |
| Текст ответа | `choices[0].message.content` (строка) | `response.content` — **список блоков**, текст в блоках `type == "text"` |
| Почему остановилась | `finish_reason`: `stop`, `length`, `tool_calls` | `stop_reason`: `end_turn`, `max_tokens`, `tool_use`, `refusal` |
| Токены | `usage.prompt_tokens` / `completion_tokens` | `usage.input_tokens` / `output_tokens` |
| Стриминг | `stream=True`, итерировать chunks | `client.messages.stream(...)` и `stream.text_stream`, итог через `stream.get_final_message()` |
| Ошибки | `openai.RateLimitError` и т. д. | `anthropic.RateLimitError` и т. д. (имена почти те же) |
| `temperature` | Есть | У текущих моделей убран, вместо него `effort` |
| Кэширование промпта | Зависит от провайдера | Явное: `cache_control` на блоках промпта или на всём запросе |

Ещё два отличия Claude, которые важны в продакшене:
- **`stop_reason == "refusal"`**: модель может отказаться отвечать по соображениям безопасности. Это нужно проверять так же, как обрезанный ответ. Для этого случая у API есть параметр `fallbacks`: запрос автоматически повторится на запасной модели.
- **Prompt caching.** Повторяющееся начало запроса (system prompt, документы) можно закэшировать. Чтение из кэша стоит малую долю обычной цены входа, запись в кэш дороже обычной (×1.25 при хранении 5 минут). Проверяется по полям `usage.cache_read_input_tokens` и `usage.cache_creation_input_tokens`. Принцип из part 1 (шаг 11.3) тот же: стабильное — в начало, переменное — в конец.

Именно поэтому полезно держать вызовы LLM за своим модулем вроде `llm_client.py`: остальной код не знает, какой провайдер внутри, и переход на Claude затрагивает одно место.
